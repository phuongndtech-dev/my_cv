Performance .NET 8 · Azure 14s → 2.5s · 82% reduction

From 14 seconds to 2.5: SemaphoreSlim done right

An API consumed by 8+ products had p95 latency around 14 seconds. Naive parallelization made it worse. The right answer was controlled concurrency — and a deeper lesson about backpressure.

The problem. A Location API consumed by 8+ downstream products had p95 latency around 14 seconds for address lookup. Users were complaining; downstream services were timing out and retrying, amplifying the load. The API was making serial calls to Google Places and Geocoding for each request, sometimes 5–10 external calls per lookup.

The naive fix that didn't work. First instinct: wrap the calls in Parallel.ForEach or unbounded Task.WhenAll. This made things worse. Google's APIs have rate limits per second, and firing 10 concurrent calls from every request quickly hit 429 throttling errors. The retries on top of throttling pushed latency higher than the original serial version.

Root cause analysis. Two separate problems were tangled together: serial I/O when parallelism was safe, and unbounded parallelism when rate limits required throttling. You can't fix the second by ignoring the first; you need controlled concurrency.

The fix. Replaced unbounded parallelism with SemaphoreSlim-controlled concurrency. The semaphore caps simultaneous outbound calls to a tuned number (high enough to parallelize, low enough to stay under rate limits). Code pattern:

private static readonly SemaphoreSlim _gate = new(maxConcurrency: 8);

                            public async Task<Result> LookupAsync(Address addr, CancellationToken ct)
                            {
                                await _gate.WaitAsync(ct);
                                try
                                {
                                    return await _googleClient.GeocodeAsync(addr, ct);
                                }
                                finally
                                {
                                    _gate.Release();
                                }
                            }

Combined with smart batching (group similar lookups, dedupe before calling), p95 dropped from ~14s to ~2.5s — a 5.6× improvement. Tail latency stopped causing downstream cascades.

Bonus win. The same pattern applied to a separate CityMapping job gave a 10× speedup on a nightly batch.

Lesson. "Make it parallel" is not a strategy. Concurrency without throttling is just a faster way to hit rate limits. SemaphoreSlim is the right primitive when you need parallelism with backpressure — and it works just as well for in-memory bottlenecks (DB connection pools, expensive computations) as for external APIs.

Migration .NET 8 · Clean Architecture · CQRS 100% data integrity · zero downtime

Migrating a 5-year-old survey monolith without losing a single response

Thousands of historical surveys, referenced by HR and compliance, had to migrate from ASP.NET MVC 5 to .NET 8 Clean Architecture without a single lost response. The migration code itself became a CQRS command — and that decision saved us twice.

The problem. A legacy survey platform built on ASP.NET MVC 5 / OWIN had served the company for 5+ years. New features were getting harder to add: auth was tied to the framework, business logic lived in controllers, and the data model assumed a single survey shape. Meanwhile, V2 needed branching logic, AI-assisted creation, richer analytics, and a Vue 3 frontend.

The constraint that mattered most. Thousands of historical surveys and responses were live data — referenced by HR, compliance, and internal reporting. Losing or corrupting any of them was unacceptable. Migration had to be 100% lossless and rollback-safe.

Architecture choice. V2 was rebuilt on .NET 8 with Clean Architecture and CQRS via MediatR. The reason wasn't fashion — it was that the migration logic itself needed to be a first-class command (MigrateFromV1Command with its handler), testable in isolation against real V1 data snapshots before touching production.

Migration strategy. Three principles:

  • Map everything explicit. Every V1 question type was mapped to a V2 equivalent in code, not magic. Unsupported types were explicitly skipped with logged reasons, not silently dropped.
  • Idempotent handlers. The migration command could be re-run without duplicating data. Each V1 record had a stable ID that V2 used as a uniqueness key.
  • Dry run first. Migration ran end-to-end against a staging copy of production data, with diffs verified before a single row was written to V2 production.

Result. Zero user-reported data loss. Permissions, response history, and survey structure preserved exactly. The dry-run discipline caught two edge cases that would have corrupted matrix-question responses if shipped blind.

Lesson. When the constraint is "don't lose data," the migration code deserves the same architectural care as the product itself. A handler with tests beats a one-off SQL script every time. The cost of writing it as a CQRS command was a few extra hours; the cost of corrupting historical data would have been measured in trust.

Modernization .NET Framework 4.8 → .NET 8 Minimal API millions of records · public-facing

Modernizing a CDN download service: three traps in a "simple" .NET migration

"Port the controllers, swap NuGet, redeploy." The plan was simple. Production found three traps that don't show up in any migration guide: a redirect loop, a thread-pool deadlock waiting to happen, and a content type that silently broke analytics.

The problem. An internal CDN download service ran on .NET Framework 4.8 — a public-facing endpoint serving millions of file requests. It worked, but maintenance was getting expensive: no first-class Linux support, slower deployments, and an Azure stack moving toward .NET 8 Minimal API everywhere else.

What looked simple. "Port the controllers, swap NuGet packages, redeploy." That was the plan. The reality had three traps that don't show up in any migration guide.

Trap 1: The 307 redirect loop. After cutover, certain download URLs entered a 307 → 307 → 307 loop. The cause was a difference in how .NET 8 handled trailing-slash normalization combined with HTTPS redirection middleware ordering. The fix wasn't a config tweak — it was reordering the middleware pipeline so HTTPS upgrade happened before route normalization, not after.

Trap 2: ZIP streaming broke under .NET 8. The legacy code streamed multi-file ZIPs back to clients using synchronous Stream.Write. Kestrel under .NET 8 disables synchronous IO by default, with good reason — it can deadlock the thread pool. The pragmatic fix was setting AllowSynchronousIO = true only on the ZIP-streaming endpoint, with a TODO to refactor the ZIP library to async streams as a follow-up. Don't enable it globally; that's how you trade one bug for a worse one.

Trap 3: The tracking pixel. A 1×1 GIF used for download analytics was returning a different content type after migration, breaking downstream analytics ingestion. The Framework version had silently inferred MIME from the file extension; Minimal API required an explicit Results.File(bytes, "image/gif"). Easy to miss, easy to fix once spotted.

Bonus. Built a public file-access statistics dashboard on top of Application Insights using KQL queries — millions of records aggregated into per-day, per-file views, replacing a Power BI report nobody wanted to maintain.

Lesson. A ".NET 4.8 → .NET 8 port" sounds like a refactor, but it's really three separate migrations stacked: the runtime, the hosting model (System.Web → Kestrel), and the API surface (Controllers → Minimal API). Each one has its own footguns. Plan canary deploys and monitor 4xx/5xx ratios closely for the first week; the bugs surface in production traffic patterns, not in unit tests.

Debugging .NET · FluentValidation · MediatR intermittent · only under load

The intermittent 500: a FluentValidation concurrency bug only load could expose

Rare 500s in production, never reproducible locally. The stack trace pointed at framework code. KQL with timestamp clustering was what cracked it — the bug had been live for months, masked by low concurrency.

The problem. An internal access-management service was throwing intermittent 500s in production. The errors were rare — maybe 1 in every few hundred requests — and never reproducible locally. Application Insights showed a Dictionary InvalidOperationException deep inside a FluentValidation pipeline behavior, but the stack trace pointed at framework code, not application code.

Why it didn't reproduce. Dev and staging had low concurrency. Each request validated cleanly. Local profilers showed nothing. The bug only surfaced when multiple requests hit the same validator instance concurrently — a condition that only existed at production load.

Investigation. KQL queries on Application Insights, correlating timestamp clusters with the failing endpoint, showed the errors clustered tightly during burst traffic. That alone hinted at concurrency. Reading the FluentValidation pipeline behavior carefully revealed the issue: the behavior was running multiple validators in parallel via Task.WhenAll, and they were all writing to a shared Dictionary<string, ValidationFailure> — which is not thread-safe for writes.

Root cause. Parallel validators were colliding on a shared dictionary. Most of the time the writes happened far enough apart in time that they didn't collide; under burst load, they did, and the dictionary's internal state got corrupted, throwing on the next read.

The fix. Two changes, in order of safety:

  1. Each validator wrote to its own local result, and the pipeline behavior aggregated them after all tasks completed — no shared mutable state during parallel execution.
  2. Where aggregation across validators was unavoidable, swapped Dictionary for ConcurrentDictionary as a safety net.

500s dropped to zero on the next deploy. The bug had been in production for months, masked by low concurrency.

Lesson. "Works in dev, fails in prod" is almost always a concurrency or environment story. When a stack trace points at framework code with no obvious application-level cause, look for shared mutable state being touched in parallel. The fix isn't always ConcurrentDictionary — often the right answer is "don't share state at all," then aggregate at the end. KQL with timestamp clustering is one of the fastest ways to confirm a concurrency hypothesis without being able to reproduce locally.
